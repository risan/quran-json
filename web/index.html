Quickstart

Everything is a GET on a JSON file. Chapter files number their verses 1..n with the key id; a translation file carries the translation only, so the Arabic and the translation are joined on that id.

One chapter, one script

curl -s https://quran-json.risanb.com/text/{{default_script}}/chapters/2.json | head -c 400
const base = "https://quran-json.risanb.com";
const chapter = await fetch(`${base}/text/{{default_script}}/chapters/2.json`).then((r) => r.json());

chapter.verses[254].text; // 2:255, Ayat al-Kursi
import httpx

base = "https://quran-json.risanb.com"
chapter = httpx.get(f"{base}/text/{{default_script}}/chapters/2.json").json()

chapter["verses"][254]["text"]  # 2:255, Ayat al-Kursi

Join the Arabic to a translation

const [arabic, translated] = await Promise.all([
  fetch(`${base}/text/{{default_script}}/chapters/2.json`).then((r) => r.json()),
  fetch(`${base}/translations/{{default_translation}}/chapters/2.json`).then((r) => r.json()),
]);

const verses = arabic.verses.map((verse, i) => ({
  id: verse.id,
  text: verse.text,
  translation: translated.verses[i].translation,
}));
arabic = httpx.get(f"{base}/text/{{default_script}}/chapters/2.json").json()
translated = httpx.get(f"{base}/translations/{{default_translation}}/chapters/2.json").json()

verses = [
    {"id": a["id"], "text": a["text"], "translation": t["translation"]}
    for a, t in zip(arabic["verses"], translated["verses"], strict=True)
]

Join on id, not on position. Every translation is keyed to the Hafs count, and every verse file numbers its verses 1..total_verses, so the lists line up — but the two riwayat scripts (warsh, qalun) number 6,214 ayahs and carry a number_in_hafs map instead.

Build an audio URL

// everyayah.com — surah-relative ayah, both padded to three digits
// (reciters.json: host.indexing_mode == "surah-relative")
`https://everyayah.com/data/Alafasy_128kbps/${String(2).padStart(3, "0")}${String(255).padStart(3, "0")}.mp3`

// cdn.islamic.network — the GLOBAL ayah number, 1..6236, unpadded
// (reciters.json: host.indexing_mode == "global-ayah"); 2:255 is ayah {{global_ayah_2_255}}
`https://cdn.islamic.network/quran/audio/128/ar.alafasy/{{global_ayah_2_255}}.mp3`

/audio/reciters.json publishes each host's indexing_mode, surah_pad and ayah_pad, so a client can fill a template without parsing the prose. Global ayah numbers come from summing total_verses in /chapters.json.

{{script_count}} text scripts

Three different things hide inside the word “script”, and this dataset carries two of them: the riwayah (which reading — Hafs, Warsh, Qalun), the rasm (how it is written — Uthmani, Imlaei, Indo-Pak) and the print layout (13/15/16-line, ayet-berkenar, Bombay), which no verse array can describe because it is page geometry rather than text. Fonts, and why they are published here

The dataset publishes UTF-8 text and names no font — render it however you like. This site does ship Arabic typography for all {{script_count}} scripts, so the table below is measured at build time from the bundled font files against every codepoint each script's verses and the chapter names use. Under each font, yes means it covers every one of them, and a number is how many codepoints it cannot render at all — hover for which. A script's default is the first font in preference order that is complete for it.

{{font_columns}} {{font_rows}}
ScriptCodepointsDefault

Coverage is not shaping. A font that carries a glyph still positions these marks by its own rules; only the typeface a text was designed for renders it as intended. indopak is DigitalKhatt's own typesetting and uses Arabic Extended-B marks (U+089C, 2,098 of them), which Amiri lacks entirely — so this site never renders indopak in Amiri, and the reader disables any font/script pair in that table that is incomplete.

Reading a script

  • indopak keeps the Indo-Pak segmentation of Al-Fatiha: the basmala is unnumbered there, so 1:1 is اَلْحَمْدُ لِلّٰهِ — the last two verses are held separately — and no basmala is embedded in any verse, because the source prints it as chapter furniture. Every chapter still has its canonical count; only chapter 1's labels differ.
  • kemenag is not a Tanzil text with another label. It is the Mushaf Standar Indonesia served by the ministry's own API: it writes no alef wasla where Tanzil's Uthmani writes 13,819 of them, and only 6 of 37,416 verse comparisons against the Tanzil variants coincide.
  • Every script says how its verse ids relate to the Hafs count that every translation is keyed to. verse_ids is hafs (the ids are Hafs numbers), mapped (a riwayah with its own count of 6,214, each verse carrying the number_in_hafs it covers) or own, and verse_ids_differ_in names the chapters whose labels are not Hafs numbers. Today that is indopak chapter 1, where the basmala is unnumbered — so the reader refuses to pair a Hafs-keyed translation with it rather than pairing the wrong verses.
  • simple is an orthography, not a lower level of vocalisation. It carries the full set of harakat; reach for simple-clean if you want the text without them.

Joining a riwayah to the Hafs count

warsh and qalun number 6,214 ayahs to Nafiʿ's count, not the Kufi 6,236, so 50 surahs differ in length from /chapters.json (al-Baqarah 285 where Hafs has 286, At-Tawbah 130 where Hafs has 129). Each verse carries the source's own number_in_hafs. There is no constant offset to add: Nafiʿ splits Hafs 2:255 across two of its verses and merges two Hafs verses elsewhere, so the join is a lookup. 

const warsh = await fetch(`${base}/text/warsh/chapters/2.json`).then((r) => r.json());

// every riwayah verse that covers Hafs 2:255
const covering = warsh.verses.filter((verse) => verse.number_in_hafs.includes(255));
// → two verses: the first half of Ayat al-Kursi, then the rest of it

{{translation_count}} translations

Each edition is published on the strength of its own grant from its own publisher, recorded per entry in /translations/index.json and in /meta/sources.json. direction is rtl for the editions written right-to-left; version is the source's version, which QuranEnc's terms require a republication to state. Translation files carry the translation only — the Arabic is identical across editions and lives once under /text/.

Recitations follow their own riwayah. The Hafs recitations do not match the warsh or qalun verse numbering, so the reader offers surah-level audio for those scripts and disables per-ayah playback rather than playing the wrong ayah.

Compatibility contract

  • A published path is never renamed, removed or rewritten. Data paths are cached immutable for a year, so a rewrite would strand consumers on stale bytes.
  • Adding is always fine: new scripts, new editions, new chapters.
  • Correcting the Quran text would be a break and would need new paths, not edited ones.
  • The frozen 3.1.2 tree on jsDelivr is the exception: it is a byte-for-byte reproduction of what npm already served, and it is not regenerated.
